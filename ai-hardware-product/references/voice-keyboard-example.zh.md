# 中文交接示例：可配置按键与设备录音

这是填写产品记录的方法示例，适用于“几个可配置按键、麦克风、蓝牙、充电电池、指示灯，按住说话后网页显示一句摘要和三条要点”。它没有指定已验证的板卡、固件或接收程序；硬件状态均为 `not_run`。沿用当前项目的已确认选择，替换下面的提案，勿把示例值当作用户要求。

## 先确定能继续实施的下一步

把要求写入 [产品记录](../assets/PRODUCT_RECORD.md)，从现有对话提取目标电脑系统、已有器材、按键动作和录音长度。确实缺少时，只询问影响当前方案的选择，例如“用哪台电脑，是否能安装接收程序”。板卡、引脚、充电方案和采购价格由 Agent 查实际来源；不要求初学者先选芯片。

若板子已下单，先取得此次制造文件、BOM 和板号，以该版本继续准备固件、接收程序与测试步骤。物流文字是历史记录，不能据此断言已经到货。尚无板卡时也能先定义数据接口、录音 ID 和网页输出，测试这些软件部分。

| route_id | 方案 | 本路线需要确认的实物条件 | 可以共用的工作 |
|---|---|---|---|
| NS | 免焊模块路线 | 现成板/模块的完整型号及版本、麦克风、预焊连接器、线缆与电池极性；所有连接可插接 | 音频文件约定、电脑接收/AI/网页接口、测试语料 |
| DIY | 自焊 PCB 路线 | 当前原理图/PCB/BOM、装配方法、器件朝向、下载接口、固件引脚配置 | 同上；电气连接、固件目标与功耗分别验证 |
| shared | 两路线共用部分 | 接口或软件版本，以及实际适用的路线 | 只记录一次，共用不代表两路线都已通过 |

购买“成品模块”不一定免焊：核对排针是否已经焊好、所需转接和线缆是否包括在内。免焊路线无需为了流程完整而新画 PCB。也不能把设备麦克风替换成电脑麦克风，或以 USB 测试通过代替蓝牙音频验收；如作为临时开发路径，另列状态即可。

## 保留可配置按键这个功能

以下是供确认的映射提案，不是固定按键数或产品默认值。

| 控件 ID | 提议动作 | 配置与生效方式 | 对应测试 |
|---|---|---|---|
| K1 | 按住录音，松开发送 | 产品配置项；具体存储位置和通信命令待定 | 录音中修改映射的行为须确定；不能意外结束或重复提交当前录音 |
| K2 | 打开最近一次结果，可改为其他动作 | 保存后读回当前映射；重启保持策略待定 | 改为另一动作，读回并触发；重启设备/电脑后检查是否符合约定 |
| K1+K2（如需要） | 用户选择的组合动作 | 与单按/长按的优先级待定 | 组合键只触发约定动作，不误生成两次单键操作 |

为需求分别保留 ID：`R-KEYMAP`（改映射及持久化）、`R-AUDIO`（设备录音到网页）、`R-POWER`（充电/续航）。固定映射录音成功只能证明 `R-AUDIO` 的相应部分。

## 把接口和一次录音对应起来

先固定接口内容，再写各端实现；字段可以按实际协议调整。

| 接口 | 至少需要对齐的信息 | 当前证据 |
|---|---|---|
| 麦克风 → 固件 | 型号/接口、引脚、采样格式、通道、采样率、最大时长 | `unknown`，等待实际板卡与驱动 |
| 固件 → 接收程序 | `recording_id`、序号/总长、格式、结束标记、校验、确认及重传/去重方式 | `planned`，先编接口测试 |
| 接收程序 → AI | 原始文件与 ID、服务/模型、原文转写、处理状态 | `planned`，可先用明确标为测试样本的文件验证 |
| AI → 网页 | 同一 ID、原文与修订文本分别保存、一句摘要、三条要点、失败重试 | `planned`，与设备测试分开记录 |

容量示例仅演示算术：假设 30 秒、16 kHz、16 bit、单声道未压缩 PCM，则音频负载为 `30 × 16000 × 2 = 960000 bytes`。若实测有效负载速率为 `20000 bytes/s`，仅该负载就需 48 秒；这不是蓝牙速率承诺。协议开销、缓存余量、传输是否与录音重叠，以及 AI 时间需另算。压缩音频改用 codec 的码率上界或最大帧长，不套 PCM 公式。参数未确认之前，不据此锁定存储器或电池。

## 从第一天记成本、时间与 AI 用量

| route_id / 记录 ID | 内容 | 记录方式 |
|---|---|---|
| NS / Q-NS-01 | 模块、线缆、电池、外壳及运费 | 使用量、实际采购量、MOQ、报价日期与来源；未询到的价格为 `unknown` |
| DIY / Q-DIY-01 | PCB、BOM、装配、工具与运费 | 拆分裸板/包料/装配口径；与 NS 分别算总价 |
| shared / T-RECEIVER | 电脑接收程序开发 | 动手时间与等待时间分列；返工属于动手时间子集，不重复相加 |
| shared / AI-DEV-01 | 开发 Agent 帮忙写固件或审图 | `purpose=development`，任务 ID、服务/模型、提供商实际报告的用量及费用 |
| NS / clip-001 | 一次录音的转写与摘要 | `purpose=runtime`，`recording_id=clip-001`，音频分钟、报告的 token、费用分列 |

示例：若 BOM 元件合计 6 元，其中电池 BAT1 为 5 元，另有已知费用 79 元，则总计为 85 元；不要再加一次 BAT1 算成 90 元。使用 PCB Skill 的 `product_total_cost.py` 时，BOM 已含电池就不再声明独立 battery 费用，用 `not_required_costs.battery` 注明“已含在元件报告 BAT1，无需另计”。此说明不免除电池的实物验收。包料 PCBA 同理，注明实际覆盖内容。这里的金额是算术例子，不是市场报价。

比较两条路线时说明共用工具或开发工作的分摊方式；不要把两条互斥采购方案相加当作一台设备的花费。开发用量与产品运行用量分别合计。拿不到提供商记录时保留 `unknown`，不从工作时长推 token，也不把订阅视作每次任务免费。

## 给下一位同伴的测试任务

每次回传包含 route_id、需求/测试 ID、代码提交、板卡/固件/电脑版本、预先约定的判据、实际结果和原始文件。已知具体版本再填入，未做就保持 `not_run`；缺硬件或程序则写 `blocked` 和缺项。

1. `R-KEYMAP`：改一个按键映射，读回、触发并重启验证；检查实际支持的单按/长按/组合规则。
2. `R-AUDIO`：用设备麦克风录制已知内容，按 ID 核对原始音频、接收文件、转写、摘要及三条要点；补最长录音、连续操作和断连重试。软件样本通过只标记电脑端。
3. `R-POWER`：拿到准确板卡、电池和充电器件资料后确定判据，分别记录输入/电池电流、录音/传输/待机状态与实际续航。
4. `R-BUILD`：选一条具体路线，交给未参与开发的同伴，按准确物料、连接图、固件目标、安装/运行/恢复命令复现；记录卡住的步骤，再修教程。另一条路线仍单独待测。

公开进度保持简短：做了什么、结果在哪里、接下来谁能测什么。完整数据留在产品记录和代码仓库，不把拟定方案写成已完成样机。
